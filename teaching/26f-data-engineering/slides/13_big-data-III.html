Batch and Stream ProcessingBatch processes a bounded set; streaming updates results as more events arrive

The difference is how ongoing input becomes an updated result

The Same Readings, Different UpdatesThe same count can be computed after a batch or updated during a stream

Streaming makes a current result available before the input stops

The First Record in a LogA log appends incoming events in order

E1 occupies position 0 in the stored log

New Readings Append at the End

A Late Reading Still Appends Last

Producer, Log and ConsumerThe producer writes events; the consumer reads them

Writing a reading and processing its result are separate steps

LinkedIn Needed Fresh Activity DataActivity logs became inputs to live services as well as later analysis

The same event data had to reach both live services and batch analysis

Kafka Begins at LinkedInKafka was open-sourced in 2011 to deliver activity records to online and offline systems

A shared log connected the activity producers to different readers

Kafka Holds the Event Log

The topic gives the event stream a name

Decoupling Writers and ReadersA retained log lets writers and readers work at different times

A new reader can use the log without adding a new producer connection

Two Readers, Two PositionsIndependent readers can consume the same retained events at their own pace

The display resumes at E4; the report resumes at E2

Partitions Split a Topic into LogsA partition is one ordered log inside a topic

M1 readings stay together in partition 0

A Key Keeps One Machine TogetherHere the record key is the machine ID
