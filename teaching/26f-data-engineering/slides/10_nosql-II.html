Some MQL Principles: Dot (.) Notation

  • "." is used to drill deeper into nested docs/arrays
  • Recall: a value is atomic, a nested document, or an array of either
  • Examples:
    • "instock.qty" → qty field within the instock field
      • Only when instock is a nested doc or an array of them
        • Nested doc: its qty field
        • Array: the qty field of any document in it
    • "instock.1" → second element within the instock array
      • An atomic value or a nested document
    • "instock.1.qty" → qty field of the second document in the instock array
Note: such dot expressions need to be in quotes

Some MQL Principles: Dollar ($) NotationOperators in the key position

  • $ indicates that the string is a special keyword
    • E.g., $gt, $lte, $add, $elemMatch, …
  • Used as the “field” part of a “field : value” expression
  • If binary operator, it is usually written as:
    • {LOperand : { $keyword : ROperand }}
    • e.g., {qty : {$gt : 30}}
{qty : {$gt : 30}}
→ get values greater than 30

Some MQL Principles: Dollar ($) NotationWhy queries are written as documents

MongoDB syntax is quite different from SQL or general-purpose languages because it is a data-centric DSL (domain-specific language), designed for expressing data queries and transformations.
Why it looks like this: MongoDB works directly with data in JSON form, so instead of writing queries as SQL-style strings it represents them as JSON objects.
SELECT * FROM orders WHERE qty > 30
→
{ qty: { $gt: 30 } }

Retrieval: Basic Queries

db.collection.find(<predicate>, optional <projection>)
  • find( { status : "D"} )
    • all documents with status D
  • find ( { qty : {$gte : 50} } )
    • all documents with qty >= 50
  • find ( { status : "D", qty : {$gte : 50} } )
    • all documents that satisfy both
  • find( { $or: [ { status : "D" }, { qty : { $lt : 30 } } ] } )
    • all documents that satisfy either

Retrieval: Nested Documents

db.collection.find(<predicate>, optional <projection>)
  • find( { size: { h: 14, w: 21, uom: "cm" } } )
    • exact match of nested document, including ordering of fields!
  • find( { "size.uom" : "cm", "size.h" : {$gt : 14 } } )
    • querying a nested field
    • Note: when using . notation for sub-fields, expression must be in quotes
    • Also note: each argument of find is a document

Retrieval: Arrays

db.collection.find(<predicate>, optional <projection>)
  • find( { tags: ["red", "blank"] } )
    • Exact match of array
  • find( { tags: "red" } )
    • Some element matches red
  • find( { tags: { $all: ["red", "plain"] } } )
    • One element red, another plain
  • find( { dim: { $gt: 15, $lt: 20 } } )
    • If one element is >15 and another is <20
  • find( { dim: { $elemMatch: { $gt: 15, $lt: 20 } } } )
    • If a single element is >15 and <20
  • find( { "dim.1": { $gt: 25 } } )
    • If second item >25; quotes again for . notation

  • OR Use 0s to indicate fields you don’t want
  • Mixing 0s and 1s is not allowed for non _id fields

  • Input = collections, output = collections
  • Three main types of queries in the query language
    • Retrieval: Restricted SELECT-WHERE-ORDER BY-LIMIT type queries
    • Aggregation: A bit of a misnomer; a general pipeline of operators
      • Can capture Retrieval as a special case
      • But worth understanding Retrieval queries first…
    • Updates
  • All queries are invoked as
    • db.collection.operation1(…).operation2(…)…
      • collection: name of collection
    • Unlike SQL which lists many tables in a FROM clause, MQL is centered around manipulating a single collection

Aggregation PipelinesA list of stages, run in order

  • Composed of a linear pipeline of stages
  • Each stage corresponds to one of:
    • match // first arg of find ( )
    • project // second arg of find ( ) but more expressiveness
    • sort/limit // same
    • group
    • unwind
    • lookup
    • … lots more!!
  • Each stage manipulates the existing collection in some way
Documents flow left to right; each stage reads the previous stage’s output

Aggregation PipelinesA list of stages, run in order

  • Composed of a linear pipeline of stages
  • Each stage corresponds to one of:
    • match // first arg of find ( )
    • project // second arg of find ( ) but more expressiveness
    • sort/limit // same
    • group
    • unwind
    • lookup
    • … lots more!!
  • Each stage manipulates the existing collection in some way
  • Syntax:
    • db.collection.aggregate ( [
        { $stage1Op: { } },
        { $stage2Op: { } },
        …
        { $stageNOp: { } }
      ] )
A pipeline is an array of stage documents, executed in the order written

Grouping SyntaxOne output document per _id

$group : {
    _id: <expression>,        // Group By Expression
    <field1>: { <aggfunc1> : <expression1> },
    … }
Returns one document per unique group, indexed by _id

Grouping SyntaxAggregation functions

$group : {
    _id: <expression>,        // Group By Expression
    <field1>: { <aggfunc1> : <expression1> },
    … }
Returns one document per unique group, indexed by _id
Agg. func. can be standard ops like $sum, $avg, $max
  • Other useful accumulators:
    • $first : return the first expression value per group
      • makes sense only if docs are in a specific order [usually done after sort]
    • $push : create an array of expression values per group
      • similar to ARRAY_AGG in SQL systems with array support
    • $addToSet : like $push, but eliminates duplicates

Looking Up Other CollectionsThe four fields of $lookup

{ $lookup: {
    from:         <collection to join>,
    localField:   <referencing field>,
    foreignField: <referenced field>,
    as:           <output array field>
} }
  • For each document:
    • find documents in other coll that join (equijoin)
      • local field must match foreign field
    • place each of them in an array
  • Thus, a left outer equi-join, with the join results stored in an array
  • Can do “self-join” to find matching items, including itself, at the same location

Some Rules of Thumb When Writing Queries

  • $project is helpful to construct or deconstruct nestings (in addition to removing fields or creating new ones)
  • $group is helpful to construct arrays (using $push or $addToSet)
  • $unwind is helpful for unwinding arrays
  • $lookup is our only hope for joins. Be prepared for a mess. Lots of $project needed

MongoDB Query Language – Updates

  • Input = collections, output = collections
  • Three main types of queries in the query language
    • Retrieval: Restricted SELECT-WHERE-ORDER BY-LIMIT type queries
    • Aggregation: A bit of a misnomer; a general pipeline of operators
      • Can capture Retrieval as a special case
      • But worth understanding Retrieval queries first…
    • Updates
  • All queries are invoked as
    • db.collection.operation1(…).operation2(…)…
      • collection: name of collection
    • Unlike SQL which lists many tables in a FROM clause, MQL is centered around manipulating a single collection

Update Queries: InsertMany

  • [Insert/Delete/Update] [One/Many]
    • Many is more general, so we’ll discuss that instead
db.inventory.insertMany([
  { item: "journal",  qty: 25, size: { h: 14, w: 21, uom: "cm" }, status: "A",
    instock: [ { loc: "A", qty: 5 }, { loc: "C", qty: 15 } ], tags: ["blank", "red"], dim: [14, 21] },
  { item: "notebook", qty: 50, size: { h: 8.5, w: 11, uom: "in" }, status: "A",
    instock: [ { loc: "C", qty: 5 } ], tags: ["red", "blank"], dim: [14, 21] },
  …   // paper, planner, postcard
]);
  • Several actions will be taken as part of this insert:
    • Will create inventory collection if absent [No schema specification/DDL needed!]
    • Will add the _id attribute to each document added (since it isn’t there)
    • Will be the first field for each document by default
