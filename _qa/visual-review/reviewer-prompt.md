# 별도 검토자에게 전달할 지시

구현 설명과 기대 CSS 수치에 동의하는 대신, 고정된 실제 화면에서 방문자가 겪을 문제를 찾아라. 소스·테스트를 고치거나 자동으로 긍정 판정을 채우지 않는다. 구현자와 다른 검토자 ID를 쓰고, 맥락을 어떻게 분리했는지 기록한다.

먼저 `manifest.json`의 수정본, 완료 여부, 화면 계획, 검사 결과를 확인한다. 원본 크기로 페이지 타일을 모두 읽고, 펼침·선택·hover·focus·오류 상태를 읽는다. 이어 공통 컴포넌트를 페이지 간 비교한다. 전체 화면을 작은 썸네일로 본 것만으로 통과시키지 않는다. 요구 이미지 목록은 `manifest.units[].imageIds`다.

메뉴의 굵기가 본문 제목보다 강하지 않은가, 학력처럼 읽어야 할 정보를 작게 숨기지 않았는가, 페이지마다 같은 메뉴가 이동하지 않는가, 긴 문장과 사진 카드의 밀도가 적절한가를 판단한다. `policy.json.rubric` 여섯 질문에 구체적인 관찰과 이미지 ID를 적는다. 이전 화면이 제공되면 나빠진 점을 먼저 찾고, 이전 화면이 없으면 비교 한계를 기록한다.

지원 학생, 과제 담당자, 동료 연구자의 관점에서 원하는 정보와 다음 동작을 찾을 수 있는지도 확인한다. 범위 밖의 새로운 제안은 승인 조건과 섞지 말고 별도 제안으로 남긴다.

생성된 `review.json`의 빈 필드를 채운다. 각 검토 단위에 해당하는 모든 요구 이미지 ID를 `evidence`에 적되, 실제로 보지 않은 이미지 ID를 복사해 열람한 것처럼 쓰지 않는다. 문제마다 관찰, 근거, 상태를 적는다. 해결 뒤에는 새 수정본을 고정해 재확인한다. 열린 문제가 있거나 증거를 읽지 못했다면 `pending` 또는 `fail`을 유지한다. 검토한 버전에서 근거가 갖춰졌을 때만 `pass` 또는 `pass-with-notes`로 정한다.
